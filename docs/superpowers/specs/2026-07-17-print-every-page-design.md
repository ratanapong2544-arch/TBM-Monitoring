# ปริ้นได้ทุกหน้า — ดัก Ctrl+P ให้ fit เอง (2026-07-17)

## โจทย์

"ในทุกหน้าทำให้สามารถสั่งปริ้นหน้าเว็บได้" — ผู้ใช้ระบุเพิ่มว่า **ไม่ต้องมีปุ่ม** ขอแค่ **กด Ctrl+P แล้วออกมาถูก**

## ปัญหาจริง (วัดแล้ว ไม่ใช่การคาดเดา)

`fitAndPrint()` ที่ย่อหน้าให้พอดี A4 ทำงาน**เฉพาะตอนคลิกปุ่ม**เท่านั้น กด Ctrl+P จะข้ามมันไป เหลือแค่ `@media print` ใน `globals.css` ที่บังคับ `A4 portrait` ตายตัวและไม่ย่อขนาดเลย

Spike (`scratchpad/spike4.js`, Chrome จริง + วัด PDF ด้วย pypdf) — หน้ากราฟแนวนอนกว้าง 1600px มี 8 คอลัมน์:

| | ผลลัพธ์ | เนื้อหาที่รอด |
|---|---|---|
| กด Ctrl+P วันนี้ | 1 หน้า A4 portrait | **6/8 คอลัมน์** — COL-7, COL-8 หายเงียบ |
| มี `beforeprint` handler | 1 หน้า A4 landscape | **8/8 คอลัมน์** |

**ไม่ใช่แค่ปริ้นไม่สวย — มันตัดเนื้อหาทิ้งโดยไม่เตือน** ซึ่งกับรายงานวิศวกรรมคือข้อมูลหายและคนปริ้นไม่มีทางรู้

ผลพลอยได้: ลิงก์ viewer (`?view=1`) ที่ส่งให้เจ้าของงานปริ้นถูกไปด้วย — ปุ่มปริ้นถูกซ่อนในโหมดนั้น แต่ Ctrl+P ห้ามไม่ได้ เจ้าของงานที่กดปริ้นวันนี้จึงได้กระดาษที่เนื้อหาขาด

## หลักการ

**WYSIWYG — เห็นบนจออย่างไร ได้บนกระดาษอย่างนั้น** (ย่อให้พอดีกระดาษเท่านั้น ไม่จัดหน้าใหม่ ไม่ปลดกล่องเลื่อน ไม่เพิ่ม/ซ่อนอะไรเกินกว่าที่ `print:hidden` ทำอยู่แล้ว)

ตัดสินใจโดยผู้ใช้ 2026-07-17:
- หน้ายาว → **ย่อเท่าที่อ่านออก แล้วต่อหลายหน้า** (ไม่ย่อจนจบใน 1 หน้า)
- Data Log (ตาราง 726 แถวในกล่องเลื่อน 500px) → **ปริ้นเท่าที่เห็นบนจอ** (ไม่ปลดกล่องเลื่อน)
- Instrument / วาระตรวจวัด → **ปล่อยยาวตามจริง** (9-17 / 17-33 แผ่น) คนกดเห็นจำนวนหน้าใน print preview ก่อนกดยืนยันอยู่แล้ว

## สถาปัตยกรรม

ทุกทางที่สั่งปริ้น — Ctrl+P, เมนู File→Print, ปุ่มในแอพ — วิ่งผ่าน **handler ตัวเดียว** ที่ดัก event `beforeprint` ของ browser

```
Ctrl+P / File→Print ─┐
ปุ่มปริ้นในแอพ ────────┼─> window "beforeprint" ─> fit (วัด → zoom → @page) ─> Chrome พิมพ์
window.print() ──────┘                                                            │
                            "afterprint" <─ คืนสภาพหน้าจอ <────────────────────────┘
```

### ไฟล์ที่แตะ (3 ไฟล์ — ไม่แตะ 11 view ที่ยังปริ้นไม่ได้เลย)

| ไฟล์ | เปลี่ยนอะไร |
|---|---|
| `utils/printFit.js` | เพิ่ม `installPrintFit()` (ติดตั้ง listener ครั้งเดียว) + `setPrintTarget()` (ให้ปุ่มเฉพาะส่วน override ได้); `fitAndPrint()` คงชื่อเดิมแต่กลายเป็น setPrintTarget + `window.print()` |
| `utils/printPages.js` (ใหม่) | ตารางค่าแนวกระดาษ/โหมดย่อ ต่อหน้า + ฟังก์ชัน pure ตัดสิน (มี unit test) |
| `ui-ux-pro-max/components/Shell.jsx` | ใส่ `id="page-print-root"` ที่ div ที่ครอบ `{children}` (2 สาขา) + `installPrintFit` ผูกกับ tab ปัจจุบัน |

### ต้องรวมทางให้เหลือทางเดียว (ไม่ใช่แปะเพิ่ม)

ปุ่มเดิม 8 ปุ่มเรียก `fitAndPrint()` ซึ่งเรียก `window.print()` ข้างใน — พอเพิ่ม `beforeprint` handler มันจะไปปลุก handler ด้วย **กลายเป็นย่อซ้อนสองชั้น (zoom 0.7 × 0.7 = 0.49 เล็กจิ๋ว)** จึงต้องเปลี่ยน `fitAndPrint` ให้เป็นแค่ตัวตั้งเป้าหมายแล้วปล่อยให้ handler ตัวเดียว fit — ไม่ใช่ fit เองแล้วเรียก print

## กฎการ fit

1. **หาเป้าหมาย**: ถ้ามี override จากปุ่มเฉพาะส่วน → ใช้อันนั้น; ไม่งั้น → `#page-print-root` (เนื้อหาของหน้าที่เปิดอยู่)
2. **วัด**: ซ่อน `.print:hidden` / `.no-print` ชั่วคราวก่อนวัด (ตรรกะเดิมใน `fitAndPrint` — ไม่งั้น scrollHeight รวมของที่ไม่ได้ปริ้น)
3. **แนวกระดาษ**: จากตาราง config (ดูล่าง)
4. **ย่อ**: ถ้าย่อลงหน้าเดียวแล้ว zoom ≥ เกณฑ์ "อ่านออก" → จบใน 1 หน้า; ถ้าต่ำกว่า → ย่อพอดีความกว้าง ปล่อยความสูงไหลหลายหน้า
5. **คืนสภาพ** ที่ `afterprint`

### ทำไมไม่ให้มันวัดแนวกระดาษเอง (ข้อเสนอแรกที่ถูกตีตก)

ข้อเสนอเดิมคือ "กว้างกว่าสูง = แนวนอน" — **วัดจริงแล้วใช้ไม่ได้**:

- วัดที่จอ 1440 ได้กว้าง 1440; วัดที่จอ 1920 ได้กว้าง 1920 — **กล่องเนื้อหายืดเต็มจอเสมอ** ความกว้างที่วัดได้จึงเป็นขนาดจอ ไม่ใช่รูปทรงเนื้อหา ผลลัพธ์จะแกว่งตามว่าใครเปิดจอใหญ่แค่ไหน
- Route (1398×1714) และ ระดับหัวเจาะ (1398×1506) ทุกวันนี้ตั้งเป็น **landscape** ทั้งที่สูงกว่ากว้าง — เป็นการตัดสินใจของคน ไม่ใช่สิ่งที่สูตรเดาถูก
- Record·Segment (1440×1539 → portrait) กับ Record·Grout (1440×1323 → landscape) เป็นฟอร์มทรงเดียวกัน แต่สูงต่างกันนิดเดียวจะได้คนละแนว = ไม่ predictable

จึง**กำหนดตรง ๆ ทั้ง 18 หน้า** ตารางเดียวจบ อ่านออก แก้ง่าย

### เกณฑ์ "อ่านออก" (zoom floor)

ตัวหนังสือเล็กสุดในแอพคือ `text-xs` = **10.5px** (root font 14px ไม่ใช่ 16 — ดู memory `tailwind-root-font-14px`)

| 0.70 | 7.4px ≈ 5.5pt | กราฟ/ตัวเลขแกน — prod ใช้อยู่ ยอมรับได้ |
| 0.63 | 6.6px ≈ 5.0pt | prod ใช้อยู่ (Segment Trend) |
| 0.50 | 5.3px ≈ 4.0pt | เส้นแบ่ง — ต่ำกว่านี้ไม่ควร |
| 0.40 | 4.2px ≈ 3.2pt | อ่านไม่ออก |

**floor = 0.5** — **ยืนยันด้วย PDF จริงแล้ว (2026-07-17)** วัดขนาดตัวหนังสือบนกระดาษที่ออกมาจริงด้วย PyMuPDF:

## Test

**Unit (jest)** — `printPages.js` เป็น pure function: เลือกแนว/โหมดจาก tab, ตัดสิน auto ด้วย zoom floor, fallback เมื่อไม่รู้จัก tab; `printFit.test.js` เดิม (fitScale) ต้องไม่พัง

**End-to-end (puppeteer + Chrome จริง + pypdf)** — สคริปต์ใน scratchpad:
1. **กันของเดิมพัง**: 7 หน้าที่ปริ้นถูกอยู่แล้ว — ปริ้นเทียบ **ก่อน/หลัง** เทียบจำนวนหน้า + แนวกระดาษ ต้องเท่าเดิมเป๊ะ
2. **ของใหม่ใช้ได้**: 11 หน้าที่เหลือ — กด Ctrl+P (ผ่าน `window.print()` ซึ่งเป็น path เดียวกัน) แล้วเช็คว่าไม่มีเนื้อหาถูกตัดขวาง (นับ text ที่รอดใน PDF เทียบกับบนจอ)
3. **ไม่ย่อซ้อน**: กดปุ่มปริ้นเดิม → zoom ที่ apply ต้องมีชั้นเดียว
4. **คืนสภาพ**: หลังปริ้น `zoom`/`width` ต้องถูกล้าง หน้าจอกลับเหมือนเดิม

### บทเรียน: เครื่องมือ verify หลอกเราได้

`page.pdf({ preferCSSPageSize: true })` ของ puppeteer **ตั้งขนาดกระดาษถูก แต่ให้ Chrome จัดหน้าที่ viewport 800-1023px** (แคบกว่าความกว้างกระดาษจริง) พอต่ำกว่า breakpoint `lg` (1024px) layout ก็จัดใหม่แล้วสูงล้นไปอีกหน้า — **ไม่ใช่พฤติกรรมของ Ctrl+P จริง**

อาการหลอก: Data Log ออก 2 หน้าทั้งที่สั่ง 1, ระดับหัวเจาะ ได้แผ่นเปล่าท้าย → เกือบไล่แก้ CSS ผิดจุดไป 2 รอบ (`page-break-inside`, `min-h-screen` — ทั้งคู่ A/B แล้วพบว่าไม่ใช่สาเหตุ และถอดออกหมด)

**วิธีที่ถูก** (ใช้ใน `scratchpad/verify-print.js`): 2 ขั้น — อ่านแนวกระดาษด้วย `preferCSSPageSize` ก่อน แล้วนับหน้า/เนื้อหาด้วย `{ format: "A4", landscape }` ซึ่งให้ viewport = ความกว้างกระดาษจริง พิสูจน์ไว้ใน `scratchpad/probe-pdf-modes.js`

### ข้อจำกัดที่รู้อยู่ — ฟอร์ม Record ปริ้นตัวเล็ก (3.7pt)

ฟอร์ม Record กว้างจริงแค่ 601px แต่กล่อง `#page-print-root` ยืดเต็มจอ 1440px → ย่อตาม 1440 ได้ zoom 0.49 → ตัวหนังสือ 3.7pt + ขอบว่างสองข้างเต็มกระดาษ

**ยังไม่แก้** เพราะทางแก้ (ย่อตามความกว้างหมึกจริง) ต้องหดกล่องลงด้วย ซึ่งจะทำให้ layout ข้างในจัดใหม่ และกล่องเดียวกันนี้ใช้กับหน้ากราฟที่ recharts ตรึงขนาดไว้ = เสี่ยงพังของที่ใช้ได้อยู่ ผู้ใช้ระบุแล้วว่าฟอร์ม Record ไม่จำเป็นต้องปริ้น ถ้าจะเอาจริงต้องทำเป็น option เฉพาะหน้า (`fitContent`) พร้อม verify กราฟใหม่ทั้งชุด
